1. 다른 사람에게 가장 먼저 할 설명

기존 과제에도 질문 분류, 작업 계획, MCP 조회, 답변 작성 기능은 있었습니다. 저는 그 위에 ‘질문에 나온 대상을 빠짐없이 확인하는 검사’, ‘증상에 맞는 런북 검색’, ‘조회한 사실과 조건에 맞는 답변 검사’를 추가했습니다. 마지막으로 복잡한 요청은 작성 역할과 별도의 AI Reviewer가 다시 읽도록 구성했습니다. 모델이 말한 수치를 그대로 믿기보다, 조회한 자료와 연결해 설명하도록 바꿨습니다.

새 버전은 모든 질문에 AI를 여러 번 호출하는 방식이 아닙니다. 일반 대화는 대화 경로로 바로 답하고, 장애 요청 중에서도 단순한 요청은 Reviewer를 생략합니다.

4. 어디를 어떻게 바꿨는가

A. 이전 질문의 작업 자료와 이번 질문을 분리했습니다

문제의 성격: 대화 기록은 기억해야 하지만, 이전 장애 질문의 조사 결과·초안까지 새 질문의 근거로 섞이면 안 됩니다. 과거 화면 혼입의 모든 원인이 State 때문이었다고 단정하지 않습니다.

수정: request_state.py의 initial_state()가 요청마다 tasks, collected, draft, 검수·Reviewer 상태를 새로 만듭니다. 이전 대화는 별도의 history에만 복사합니다. 서버는 같은 대화의 겹치는 요청을 잠금으로 순서대로 처리합니다.

# 실제 코드 발췌: 매번 새로운 리스트를 만듭니다.
'history': [dict(m) for m in history],
'events': [], 'tasks': [], 'collected': [],
'draft': '', 'final': ''

request_ui.js에서는 요청 ID가 다른 늦은 이벤트를 거르고 최종 답변 중복을 방지하도록 보완했습니다. 이를 “이름 기억 기능을 새로 만들었다”고 설명하면 부정확합니다. 세션 저장은 기존에도 있었고, 작업 상태와 표시의 혼입 방지를 보완한 것입니다.

발표 표현: “기억해야 하는 대화와, 질문마다 새로 확인해야 하는 조사 자료를 분리했습니다.”

B. 모델이 짠 계획을 코드가 한 번 더 검사합니다

기존: 원본 plan_node()는 계획 모델이 만든 tasks를 받습니다. 원본 게이트는 불필요한 analysis 작업을 제거하지만, 명시적으로 요청한 모든 서비스가 조회 목록에 있는지 강제하지는 않습니다.

수정: target_scope.py의 requested_targets()가 질문에서 알려진 서비스명을 모두 찾습니다. enforce_scope()는 이 목록으로 모니터링 작업을 구성해 누락·중복·범위 밖 계획을 정리합니다.

# 실제 gate_node() 발췌
expected = state.get('requested_targets') or requested_targets(state['query'], KNOWN_SYSTEMS)
tasks, scope_report = enforce_scope(state['tasks'], expected)

예를 들어 payments-service와 cache-service를 모두 물었다면 expected는 두 이름의 목록입니다. 모델 계획이 하나만 넣더라도 코드가 두 조회 작업을 만듭니다. 조회 후에는 coverage()로 대상 이름·상태·유효한 CPU/메모리 수치를 확인합니다. 부족하면 누락 대상만 한 차례 더 조회하고, 끝내 못 얻으면 미확인으로 답합니다.

한계: 아직 지원 목록에 없는 billing-service는 기존 정책대로 auth-service로 대체됩니다. 이것을 billing-service 조사 성공으로 설명하면 안 됩니다. 또한 명시하지 않은 의존 서비스의 자동 발견은 이 범위 검사로 해결하지 않았습니다.

발표 표현: “AI가 계획을 세우되, 사용자가 요청한 서비스가 빠졌는지는 Python 코드가 검사합니다.”

C. 첫 키워드 하나로 고르던 런북을 검색으로 찾습니다

기존: 원본 _classify_incident_type()는 알림을 합친 문자열에서 규칙을 순서대로 확인하고 첫 일치의 런북 유형을 반환합니다. 매칭이 없으면 db-down으로 대체합니다. 여러 증상이 있어도 이 경로는 유형 하나를 돌려줍니다.

수정: runbook_retriever.py의 search()는 다음 순서로 찾습니다.

  1. 서비스별 알림과 사용자 질문을 각각 검색 문장으로 만듭니다. 한 서비스의 CPU 문구가 다른 서비스의 메모리 증상을 덮지 않게 분리합니다.
  2. 임베딩으로 Chroma의 여섯 런북 중 의미가 가까운 후보를 찾습니다. 짧은 런북이므로 문서 전체를 저장합니다.
  3. 관련성 필터가 후보를 고릅니다. 필터가 제시한 질문 인용·문서 인용이 실제 원문 안에 있는지도 코드로 확인합니다.
  4. 중복을 합치고 최대 두 런북을 선택합니다. 개수 제한 때문에 모든 복합 장애를 다 포괄한다고 보장하지 않습니다.
  5. retrieve_runbooks_node()가 MCP에서 원문을 다시 읽고 해시를 비교합니다. 해시는 내용의 일치 여부를 확인하며, 런북 자체의 최신성이나 옳음을 보증하지는 않습니다.

검색 실패·결과 없음은 최대 두 번의 검색 시도로 제한합니다. 근거를 못 얻으면 임의의 대응 절차를 만들지 않습니다. 현재 파일에 남아 있는 _classify_incident_type()만 보고 최신 경로도 키워드 검색이라고 설명하지 마세요. 최신 그래프의 실제 Edge는 retrieve_runbooks로 연결되어 있습니다.

발표 표현: “CPU와 메모리가 동시에 문제라면 두 증상을 따로 검색하고, 실제로 읽은 매뉴얼만 답변 근거로 사용합니다.”

D. 모델에게 긴 보고서 대신 근거 안의 ID를 선택하게 했습니다

기존: 모델이 수집 자료로 자유로운 보고서 문장을 생성했습니다.

수정: report_selection.py의 모델 출력 계약은 짧습니다.

class ReportSelection(StrictModel):
    action_ids: list[str]
    hypothesis_ids: list[str]

selection_context()는 이번 요청에만 쓰는 절차 번호 A1·A2, 가설 번호 H1·H2를 모델에 줍니다. 예를 들어 {"action_ids":["A1"],"hypothesis_ids":[]}는 형식을 보여주는 예시이며 특정 요청의 실측 출력은 아닙니다. ID의 뜻은 매 요청 달라집니다.

expand_selection()은 존재하지 않는 ID와 임의 필드를 거부하고, 실제 조회값으로 사실 부분을 구성합니다. 조치 조건이 모두 확인되지 않으면 conditional로 표시합니다. execution_status는 항상 proposed로 구성하므로, 안내만 했는데 조치를 실행했다고 표현하지 않습니다.

발표 표현: “AI는 관련 절차를 고르고, 서비스명·숫자·조건·출처는 코드가 붙입니다. 모델이 긴 문장을 만들면서 값을 바꿀 여지를 줄였습니다.”

E. 형식 검수를 근거·조건 검수로 강화했습니다

기존 실제 코드: 원본 validate_node()

ok = len(draft) >= 30 and "1)" in draft
if not ok and attempts >= 3:
    ok, verdict = True, "합격(최대 시도 도달 — 통과 처리)"

길이와 번호는 형식만 확인합니다. 올바른 서비스의 숫자인지, 런북의 적용 조건을 지켰는지는 이 검사로 알 수 없습니다.

수정: validator.py의 validate_report()가 다음을 검사합니다.

  • 근거 ID가 존재하고 대상·수치가 실제 조회값과 같은지
  • 요청한 서비스마다 상태·CPU·메모리 사실이 포함됐는지
  • 선택한 절차가 실제 읽은 런북의 허용 목록에 있는지
  • 조건이 미확인인데 즉시 조치처럼 권고하지 않았는지
  • 가설이 런북의 허용된 후보인지

현재 CPU가 높다는 값 하나로 “일정 시간 이상 지속됨”을 입증할 수는 없습니다. 지속 시간 자료가 없으면 그 조건은 unknown으로 남습니다. 숫자가 있는 알림 문장도 현재 측정 필드로 바꾸지 않고, 알림 인용으로 구분합니다.

최신 분기 코드:

if state['validation_result']['passed']:
    return 'review'
return 'write' if state['validation_attempts'] < MAX_REPORT_ATTEMPTS else 'validation_failed'

작성·코드 검수는 최초 포함 최대 3회입니다. 한도 도달을 합격으로 바꾸지 않습니다.

발표 표현: “기존에는 형식이 맞으면 통과했지만, 지금은 ‘어느 서비스의 어떤 근거로 이 말을 했는지’를 검사합니다.”

F. 복잡한 답변에는 독립 Reviewer 역할을 추가했습니다

server.py의 _build_reviewer()는 기본적으로 OpenAI용 Reviewer 객체를 별도로 만듭니다. 기본 모델은 품질 모델인 gpt-4o이며, 별도 시스템 지시문을 사용합니다. 같은 제공자·같은 모델 계열을 써도 작성과 검토는 서로 다른 역할입니다. 그렇다고 완전히 독립된 사실 확인 기관이 되는 것은 아닙니다.

semantic_review.py의 review_policy()는 코드 검수 통과·조회 자료·절차 후보 확보를 전제로, 다음 중 하나이면 검토를 요청합니다.

  • 요청 서비스가 둘 이상
  • 읽은 런북이 둘 이상
  • 비교 분석 요청
