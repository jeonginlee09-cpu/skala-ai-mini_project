기존 과제와 최종 개선본의 실제 차이

이 자료는 기존 과제 0d8405e와 최종 제품 69d58eb만 비교합니다. OpenAI 실행 경로를 중심으로 실제 코드를 대조했습니다. 19개 기능의 원본 대조표에는 근거 구절·줄 번호를 정리했습니다.

1. 먼저 설명할 핵심

기존 과제에도 질문 분류, 복수 서비스 계획, MCP 조회, 런북 기반 작성과 대화 저장이 있었습니다. 저는 이 기반 위에 요청 대상의 누락 검사, 복합 증상에 맞는 런북 RAG, 답변의 근거·조건 검수와 별도 Reviewer를 추가·강화했습니다. 저장된 대화는 운영 후속 질문의 대상 연결에도 사용하도록 보완했습니다.

구분 원본에 이미 있던 기능 최종본에서 실제로 달라진 부분
조사 대상 복수 서비스 계획, 대상 이름 보정, 중복 제거 요청 대상 전체 대조, 부분 누락 보완, 실제 조회값의 유효성 검사
런북 MCP로 런북을 읽고 답변에 사용 첫 키워드 유형 선택에서 증상별 RAG·복수 근거·원문 대조로 변경
답변 모델이 수집 자료를 보고 작성, 형식 검사 ID 선택·코드 조립, 수치·조건 검사, 복잡한 요청의 별도 Reviewer
대화 SQLite·thread_id·이름 회상, 요청별 새 그래프 입력 운영 후속 질문의 대상 연결, 모호하면 추가 질문, 새 지표 조회
화면·저장 시도별 말풍선, 최종 문자열 표시 request_id로 늦은 이벤트 차단, 검수 후 장애 답변 공개, 대화 쌍 저장
반복 재계획·도구 재시도·작성 횟수 제한 작성 한도 뒤 강제 합격을 없애고 실패 보류, Reviewer 상한 추가

FastAPI lifespan, MCP의 별도 stdio 프로세스, DI, LangGraph, LangSmith, 병렬 조회·일시 오류 재시도는 기존 기반을 유지했습니다. 이 기술들을 처음 도입했다고 설명하지 않습니다.

2. 원본과 최종본의 처리 흐름

기존 과제
질문 → 대화/운영 분류 → 계획 → 분석 게이트 → MCP 조회
     → 런북이 없으면 첫 키워드 유형으로 런북 조회
     → 필요한 경우 모델 분석 → 자유문장 작성 → 형식 검사 → 최종 답변

최종 개선본
질문·저장된 대화 → 운영 지시 대상 확인 → 모호하면 추가 질문
     → 대화/운영 분류 → 계획·요청 범위 대조 → MCP 조회·지표 누락 확인
     → 증상별 RAG → MCP 원문·해시 확인 → 필요한 경우 현재값 비교
     → Writer의 ID 선택 → Python 조립 → 사실·조건 Validator
     → 복잡한 요청만 별도 Reviewer → 최종 답변 또는 실패 보류

원본 graph.py와 최종 build_graph()를 함께 보면 추가·변경한 단계가 드러납니다. 일반 대화는 두 버전 모두 무거운 조사 경로를 건너뜁니다.

3. 복수 서비스가 처음 가능해진 것이 아닙니다

원본: OpenAIFastLLM.plan()은 서비스마다 작업을 만들도록 요청하고 대상 이름·중복을 보정합니다. 연구 작업이 하나도 없으면 질문의 알려진 대상을 복구합니다. 다만 두 대상을 요청했는데 하나만 계획된 경우, if not seen: 조건은 거짓이므로 그 복구 분기가 작동하지 않습니다.

최종: enforce_scope()가 질문에서 명시한 전체 대상과 계획을 대조합니다. 조회 후에도 coverage()로 실제 응답의 서비스명·상태·유효한 CPU/메모리·알림을 확인합니다. 부족한 대상만 한 차례 더 조회하고 끝내 못 얻으면 미확인으로 답합니다.

확인 순서 코드가 확인하는 것
계획 전후 요청한 서비스가 모두 들어갔는지, 중복·범위 밖 대상이 있는지
실제 조회 후 요청한 서비스의 응답인지, 사용할 수 있는 지표인지
제한된 보충 후 여전히 미확인인 대상은 정상으로 단정하지 않는지

발표 표현: “원본의 복수 서비스 계획에 전체 대상의 누락 검사를 보완했습니다.”

한계: 명시하지 않은 의존 서비스의 자동 발견은 구현하지 않았습니다. 미지원 billing-service의 기존 auth-service 대체 정책도 남아 있습니다.

4. 런북 선택을 키워드에서 RAG로 바꿨습니다

원본: _classify_incident_type()는 모니터링 결과의 알림을 합치고 규칙을 순서대로 검사합니다. 처음 맞는 키워드의 장애 유형 하나를 반환하며, 일치하지 않으면 db-down을 반환합니다. 원본도 이 런북을 읽어 Writer에게 제공했습니다.

최종: RunbookRetriever.search()는 다음 순서로 찾습니다.

  1. 서비스별 알림과 전체 질문을 각각 검색 문장으로 만듭니다.
  2. 임베딩과 Chroma로 현재 여섯 런북의 순위를 구합니다.
  3. 관련성 모델이 관련 문서를 고르고, Python이 질문·문서 인용의 실제 존재를 검사합니다.
  4. 중복을 합친 뒤 retrieve_runbooks_node()가 MCP에서 선택한 원문을 읽습니다.
  5. 등록 ID·내용 해시와 조건표의 일치를 확인한 자료만 권고 후보로 사용합니다.

발표 표현: “CPU·메모리·디스크처럼 독립적인 증상이 있으면 관련 매뉴얼을 각각 검색해 답변 근거로 연결합니다.”

최종본의 별도 실제 사례 F08에서는 세 서비스와 cpu-spike, memory-leak, disk-full을 확인했습니다. 이 입력의 원본 결과를 함께 측정한 것은 아니므로, 이 사례를 원본 대비 검색 정답률 개선 수치로 쓰지는 않습니다.

한계: 전체 여섯 후보를 관련성 모델에 주는 작은 자료 범위입니다. 문서가 많아질 때의 후보 축소·토큰 예산은 별도 설계가 필요합니다. 인용·해시 일치가 의미의 정확성이나 최신성을 보장하지는 않습니다.

5. 형식 검사에서 근거·조건 검수로 강화했습니다

원본: write_node()가 모니터링·런북·분석 결과로 모델의 자유문장 답변을 받습니다. validate_node()는 30자 이상인지와 1) 포함 여부를 확인합니다.

최종: ReportSelection은 모델 출력에 action_ids, hypothesis_ids만 허용합니다. 모델은 이번 요청의 허용된 절차·가설 번호를 선택합니다.

class ReportSelection(StrictModel):
    action_ids: list[str]
    hypothesis_ids: list[str]

expand_selection()은 없는 ID를 거부하고, Python이 실제 조회값으로 사실·수치·조건·출처·제안 상태를 구성합니다. validate_report()는 이 참조와 요청 대상·적용 조건을 검사합니다.

내용 최종본의 처리
현재 CPU·메모리 실제 측정 필드의 근거 ID로 연결합니다.
알림의 숫자 발생 시각 미확인 알림 인용으로 구분합니다.
원인 후보 가능성·점검 가설로 표시합니다.
적용 조건 미확인 즉시 조치로 단정하지 않고 조건부 권고로 제한합니다.
조치 실행 여부 실제 실행 도구가 없으므로 제안 상태로 표시합니다.

원본에도 AI 계획과 Python 게이트의 역할 분리가 있었습니다. 최종본에서는 Writer가 결정하는 범위를 ID 선택으로 좁히고, 사실·조건의 구성을 코드로 옮겼다는 차이가 있습니다.

별도 Reviewer를 추가한 이유

원본에는 계획·조사·분석·작성 역할이 있었지만 별도 내용 검토 노드는 없었습니다. 최종본은 코드 검수 후 복잡한 요청에 Reviewer가 질문의 누락·관련성·원인 단정을 검토하도록 했습니다.

첫 반려는 Writer로 돌아가며 코드 검사도 다시 받습니다. Writer는 최초 포함 최대 3회, Reviewer는 최대 2회입니다. 원본에도 작성 횟수 제한이 있었고, 최종 차이는 계속 실패했을 때 강제 합격 대신 보류한다는 점입니다.

한계: Reviewer는 새 측정값을 조사하지 않으며 사람 승인이 아닙니다. 모델의 의미 오판은 남아 있습니다. 코드 검사도 등록된 참조·조건 범위의 검사입니다.

6. 대화 저장을 운영 후속 질문에도 연결했습니다

원본: server.py는 thread_id로 SQLite 대화를 읽습니다. 일반 대화는 이를 사용하지만 운영 분류·계획은 현재 질문을 사용합니다. 이름 회상과 대화 저장 자체는 이미 있었습니다.

최종: resolve_followup()이 최근 사용자 메시지의 서비스 이름을 찾아 작업용 effective_query에 연결합니다.

  • 현재 질문이 새 서비스명을 명시하면 그 이름을 우선합니다.
  • 앞에 두 서비스가 있는데 “그 서비스”라고 하면 어느 것인지 되묻습니다.
  • 대상이 연결된 운영 질문은 조회 경로로 보내 현재 지표를 새로 확인합니다.
  • 이전 측정값과 AI 답변의 서비스명을 새 근거로 복사하지 않습니다.

server.py는 같은 대화의 요청을 순차 처리하고 append_turn()으로 사용자·답변 쌍을 함께 저장합니다. 실패 초안을 성공 답변으로 저장하지 않습니다.

화면에도 원래 시도별 말풍선·최종 문자열 처리가 있었습니다. 최종 request_ui.js는 request_id로 늦게 도착한 이벤트를 거르고 완료·실패를 종료 상태로 처리합니다. 검수 전 장애 초안은 공개하지 않습니다. 이 보완을 “기억 기능을 처음 구현했다”거나 과거 혼입의 원인을 모두 State로 확정했다고 설명하지 않습니다.

한계: 제한된 한국어 지시 표현과 최근 10개 메시지 범위입니다. 범용 대명사 해석이나 LangGraph Checkpointer 전환을 구현한 것은 아닙니다.

7. 기존 기술을 어떻게 이어 썼나요?

기존 기반 유지·확장한 방법
FastAPI lifespan·DI 기존 객체 준비·주입 방식에 검색기·Reviewer를 추가했습니다.
MCP 같은 클라이언트로 Tool·Resource·Prompt를 계속 사용합니다.
LangGraph·LangSmith 그래프에 검색·검수·맥락 노드를 연결하고 기존 추적으로 실행을 확인합니다.
병렬 조회·Transient 재시도 원본 방식을 유지하고 조회 결과 검사를 추가했습니다.
SSE 기존 중계를 유지하면서 일반 대화의 실제 OpenAI 조각을 messages로 받습니다. 노드 완료는 updates, 직접 MCP 진행은 custom으로 구분합니다.
모듈화 원본의 서버·모델·MCP·세션 구분 위에 검색·근거·조건·선택·검토 모듈을 나눴습니다.

비교 분석도 원본에 있었습니다. 최종본은 별도 모델의 패턴 요약 대신 검증된 현재값을 코드로 비교합니다. 시계열·배포 이력·호출 관계가 없으므로 공통 원인은 확정하지 않습니다.

8. 실제 수치와 발표에서 구분할 것

동일 입력 실측은 원본·최종본 각각 33건입니다. 평균 시간은 4.207초→3.246초, 전체 모델 토큰은 29,671개→74,252개입니다. 근거와 Reviewer 입력이 추가되어 토큰이 늘었습니다. 개별 변경의 효과를 분리한 실험은 아닙니다.

이번 실행의 조회 대상 정책 일치는 양쪽 모두 24/24건이므로 조회 정확도가 높아졌다고 주장하지 않습니다. 자동 처리 완료·Validator 통과·Reviewer 승인은 독립 평가자의 답변 정답률이 아닙니다. 추가 기능 10건은 최종본의 동작 확인으로 구분했습니다.

기술 개념의 수업자료 근거는 유지합니다. AI Agent 설계 및 구축 p.41·74~75는 Chroma·RAG, p.108·116~118은 역할 분리·검토를 설명합니다. Capstone p.148·155·165·170은 게이트·재계획·검수·반복 방지, p.209는 대화 지속성, p.217·219·221은 모듈·DI·테스트입니다. 정확한 필드명과 현재 횟수·보류 정책은 프로젝트의 구현 선택입니다.

발표에는 원본 대조표, 실제 응답, 실측 표를 근거로 사용하면 됩니다. 이번 수정은 설명자료·PPT 수정이며 제품 코드와 이미 확보한 실측값을 바꾸지 않았습니다.
