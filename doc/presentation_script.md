# 5분 발표문

**3반 G092 이정인 / 과제 1: Base AI Project 개선하기**

앞 2분은 기능·결과, 뒤 3분은 추가 코드와 한계입니다. 시간은 계획이며 실제 리허설로 조정합니다. PPT 발표자 노트와 같은 원고입니다.

## 1. 운영 인시던트 Agent 개선 (0:00–0:15)

안녕하세요. 3반 G092 이정인입니다. 과제 1인 Base AI Project 개선하기를 선택했습니다. 운영 인시던트 대응 Agent의 조사 범위와 런북 검색, 답변 검수를 보완했습니다.

## 2. 추가·수정한 기능 (0:15–0:55)

기존에도 MCP 조회와 런북 기반 작성, 복수 서비스 계획과 대화 저장이 있었습니다. 저는 전체 요청 대상과 실제 조회값을 대조하는 검사를 보완했습니다. 런북은 첫 키워드 유형 선택에서 질문과 서비스별 알림을 활용하는 RAG로 바꿨습니다. Writer는 절차 ID를 고르고 코드가 사실과 조건을 조립하도록 했으며, 복잡한 요청에 별도 Reviewer를 추가했습니다. 운영 후속 질문의 대상과 늦은 화면 이벤트도 구분했습니다.

## 3. 동일 질문의 실행 결과 (0:55–1:20)

화면은 같은 메모리 질문을 최종본에서 실제 실행한 결과입니다. 원본은 현재 메모리 89퍼센트에도 즉시 재시작을 권고했습니다. 최종본은 현재값, 원인 가설, 미확보 자료와 런북 출처를 나눕니다. 실제 조치는 실행하지 않습니다. 이 캡처 시연은 다음 통계와 별도로 기록했습니다.

## 4. 기존 과제와 최종본 실측 (1:20–2:00)

같은 열한 개 입력을 버전별 세 번씩 실행해 총 예순여섯 건을 비교했습니다. 평균 시간은 4.207초에서 3.246초로 약 22.8퍼센트 줄었습니다. 반면 토큰은 29,671개에서 74,252개로 늘었습니다. 근거와 조건, Reviewer 입력이 추가되었기 때문입니다. 조회 대상 정책 일치는 양쪽 모두 스물네 건으로 같아서 정확도 개선을 주장하지 않습니다. 캐시 준비 비용과 실제 청구액도 이 수치와 구분했습니다. 이제부터 추가 코드의 흐름을 설명하겠습니다.

## 5. Agent Graph 구성 (2:00–2:45)

먼저 Graph입니다. build_graph는 각 노드 함수를 State로 연결합니다. State에는 질문과 조사 결과, 검수 상태를 담습니다. 대상이 모호하면 추가 질문 후 종료하고, 운영 요청이면 계획과 MCP 조회를 진행합니다. 조사 후에는 누락 보충이나 런북 검색으로 갈라집니다. 화면 아래 실제 코드처럼 write 다음에 validate를 연결하고, 검사 결과로 review, write, validation_failed 중 하나를 선택합니다. Writer는 최초 포함 세 번까지만 작성하며, 계속 실패하면 최종 답변을 보류합니다. 모든 노드를 Agent로 만들지 않고 대상과 수치 검사는 코드가 담당합니다.

## 6. MCP 원문 연결 코드 (2:45–3:20)

MCP는 기존 통로를 재사용했습니다. 새로 연결한 부분은 retrieve_runbooks_node입니다. 먼저 런북 Resource를 제공하는 서버와 주소 양식을 찾습니다. RAG가 고른 key를 그 주소에 넣고 read_resource로 원문을 읽습니다. 이어 등록된 ID인지, 읽은 원문과 카탈로그의 해시가 같은지 확인합니다. 모니터링은 Tool, 매뉴얼은 Resource라는 역할 차이입니다. 해시는 내용 일치만 확인하며 최신성이나 정답을 보장하지는 않습니다.

## 7. RAG 검색 코드 (3:20–4:05)

다음은 RAG 검색입니다. 서비스별 알림과 전체 질문을 별도 검색 문장으로 만듭니다. CPU 표현이 다른 서비스의 메모리 증상을 덮지 않게 하기 위해서입니다. 화면의 _embed는 문장을 벡터로 바꾸고, collection.query는 Chroma에서 가까운 런북을 찾습니다. 이후 관련성 모델이 문서를 고르면 Python이 인용 문구의 실제 존재를 확인하고 MCP 원문과 연결합니다. 자료는 짧은 런북 여섯 개여서 문서 전체를 저장했습니다. 현재 전체 후보를 관련성 모델에 주므로 문서가 많을 때의 효율은 별도 검증이 필요합니다. 검색은 두 번까지만 시도합니다.

## 8. Writer·Validator·Reviewer (4:05–4:40)

Writer는 action_ids와 hypothesis_ids만 고릅니다. expand_selection이 실제 조회값과 조건, 출처를 조립하고 validate_report가 참조와 수치를 검사합니다. 이어 복수 서비스나 비교 요청처럼 복잡한 경우만 review_policy가 별도 Reviewer를 호출합니다. Reviewer는 최대 두 번이며 첫 반려는 재작성으로 돌리고, 다시 실패하면 보류합니다. AI 검토이므로 사람 승인은 아닙니다. 기존 역할 분리에 검토 역할과 실패 경로를 보완한 구조입니다.

## 9. 한계와 다음 개선 (4:40–5:00)

검수 강화로 입력 토큰이 늘었고, 샘플에는 시계열과 배포 이력이 없어 근본 원인을 확정할 수 없습니다. 이후에는 미지원 서비스의 대체 정책과 검색 입력 예산을 개선하고, 사람의 정답 채점으로 품질을 확인하고 싶습니다. 감사합니다.

## 발표 전 확인

- 1~4장까지 2분 안에 설명하고 5장에서 코드 설명으로 넘어갑니다.
- Graph는 agent/graph.py의 build_graph(), MCP는 retrieve_runbooks_node(), RAG는 RunbookRetriever.search()를 가리킵니다.
- 실시간 시연이 늦으면 PPT의 실제 캡처로 결과를 설명합니다.
- 지표는 같은 11개 입력의 버전별 33건입니다. 화면용 별도 실행과 섞지 않습니다.
- 기존 기술과 추가·수정 기능을 구분하고, 사람 승인·실제 조치는 구현하지 않았다고 설명합니다.
