# 발표문 초안

약 5분을 목표로 작성했습니다. 실제 소요 시간은 리허설로 확인해야 합니다. 각 슬라이드의 발표자 노트에도 같은 설명을 넣었습니다.

## 1번 슬라이드

안녕하세요. 이정인입니다. 기존 운영 인시던트 Agent를 개선했습니다. AI가 답을 길게 만드는 것보다, 사용자가 요청한 서비스를 실제로 조회했는지와 그 근거에 맞게 답하는지를 확인하는 데 집중했습니다. 오늘 숫자는 실제 운영 장애가 아닌 수업용 고정 샘플의 비교 결과입니다. 발표는 문제, 설계, 코드, 실측, 한계 순서입니다.

## 2번 슬라이드

원본에도 계획, MCP 조회, 런북 기반 작성, 세션 저장과 반복 제한은 있었습니다. 개선점은 그 기능의 존재가 아니라 검사 수준입니다. 원본의 런북 분류는 첫 키워드 일치 유형 하나를 고르고, Validator는 글자 수와 번호를 확인합니다. 그래서 요청 대상과 실제 결과, 수치와 적용 조건까지 확인하도록 강화했습니다. 과거 응답의 결함이 어느 코드 한 줄 때문이라고 단정하지 않고 실제 흐름과 테스트로 확인했습니다.

## 3번 슬라이드

FastAPI는 요청을 받고, LangGraph는 단계를 연결합니다. MCP는 모니터링 도구와 런북 원문을 제공합니다. 의존성 주입으로 모델과 도구를 전달하기 때문에 테스트에서는 통제된 모델과 도구로 바꿀 수 있습니다. 새로 보완한 부분은 이전 대상 연결, 조사 범위 대조, RAG, 구조화 검수, 선택적 Reviewer입니다. 모든 노드가 독립 Agent라는 뜻은 아닙니다. 작성과 검토를 별도 역할과 지시문으로 나눴습니다.

## 4번 슬라이드

런북은 장애 대응 매뉴얼입니다. 서비스별 알림과 질문을 나눠 Chroma에서 검색한 뒤 관련성 모델의 선택과 실제 인용을 코드로 확인합니다. 이전의 두 문서 제한은 교재가 요구한 규칙이 아니며 세 증상의 근거를 누락시킬 수 있어 제거했습니다. 현재 문서는 여섯 개로 작으므로 전체 후보를 확인합니다. 문서가 커지면 후보 수와 입력 토큰 예산을 새로 설계해야 합니다. 실제 F08의 세 런북 결과는 별도 실행 기록으로 남겼습니다.

## 5번 슬라이드

SQLite가 대화를 저장하는 기능은 원래 있었습니다. 하지만 운영 계획에 이전 대상을 연결하는 것은 별도의 문제입니다. 이번에는 최근 사용자 메시지에서 이름만 가져와 작업 질문을 구성합니다. 두 대상 중 하나를 가리키면 추가 질문하고, 둘 다라고 하면 둘을 새로 조회합니다. 첫 실제 검사에서 대상은 맞게 연결했지만 라우터가 일반 대화로 보내 이전 수치를 답한 문제가 나타났습니다. 그 실패를 보존하고, 대상이 연결된 운영 질문은 반드시 조회하도록 가드를 추가했습니다. 아직 모든 한국어 대명사를 처리하는 기능은 아닙니다.

## 6번 슬라이드

Writer는 긴 보고서 대신 허용된 절차와 가설의 ID를 선택합니다. Python이 실제 조회 사실과 조건을 붙이고, Validator가 존재하지 않는 ID나 바뀐 수치, 확인되지 않은 조건을 검사합니다. 복잡한 질문은 별도 Reviewer가 누락과 관련성을 읽습니다. Reviewer가 반려하면 다시 쓰고 코드 검사도 다시 받습니다. Writer 세 번, Reviewer 두 번 한도 뒤에는 강제 합격하지 않습니다. 이 횟수 조합과 보류 정책은 프로젝트 선택이며 교재의 그대로인 숫자는 아닙니다.

## 7번 슬라이드

같은 열한 입력을 세 번씩 실행해 원본과 최종 수정본 각각 서른세 건을 비교했습니다. 평균 시간은 4.207초와 3.246초, 모델 총 토큰은 29,671개와 74,252개입니다. 토큰에는 Reviewer가 포함됩니다. 검색 준비 여덟 건과 새 기능 열 건은 본 비교에서 제외하고 따로 기록했습니다. 조회 대상 일치에는 Q08의 기존 auth-service 대체 정책이 포함됩니다. billing-service를 조사했다는 뜻은 아닙니다. 자동 처리 완료와 조회 대상 일치는 답변 정답률과 다릅니다. 네트워크와 모델 변동이 있고 변경을 묶어서 비교했으므로 개별 변경의 인과 효과를 단정하지 않습니다.

## 8번 슬라이드

검사를 강화하면 모델 입력과 검토 비용이 늘 수 있습니다. 빠르다는 것과 싸다는 것은 다르므로 둘을 분리했습니다. 현재 데이터는 수업용 샘플이며 시계열, 배포 이력, 호출 관계가 없어 실제 원인을 확정할 수 없습니다. 미지원 billing-service를 auth-service로 대체하는 기존 정책도 남아 있습니다. 사람 승인과 실제 재시작, 롤백, 증설은 구현하지 않았습니다. 독립적인 사람의 의미 정확도 채점과 실제 청구액 확인도 남았습니다.

## 9번 슬라이드

코드 검사는 Python 아흔 개와 화면 처리 다섯 개를 통과했습니다. 실제 API는 같은 입력 예순여섯 건과 별도 기능 열 건을 실행했고, 84개 그래프 추적을 재조회했습니다. 원문 해시, 고정 지표, 제공자 토큰을 대조해 숫자를 재현할 근거를 남겼습니다. 발표 시에는 F08의 세 증상 조회, F02의 후속 질문, F05의 모호한 대상 확인을 시연할 수 있습니다. 다음은 독립 평가자의 의미 정확도 채점과 미지원 서비스 정책, 문서가 많아질 때의 입력 예산 개선입니다. 감사합니다.
